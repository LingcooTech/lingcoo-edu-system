# UI 架构与标准

本项目 Admin UI 直接对齐 `lingcoo-core-stack` 的后台方向：资源式控制台，而不是“大设置页”或营销页。

## 1. UI 架构原则

- 固定后台 Shell：左侧导航、顶部条、页面标题、资源内容区。
- 资源页优先：每个业务域先抽象成资源列表，再进入详情、表单和动作。
- 表格优先：后台运营场景默认用列表和表格承载主信息。
- 状态语言统一：统一使用 `StatusPill` 表达业务状态。
- 页面配置集中：导航、分组、页面标题和描述集中在 `src/lib/foundation.ts`。
- 路由即边界：每个资源页只加载本页需要的数据。

这与功能架构一一对应：

- `crm` → 线索
- `trial` → 公开课
- `catalog` → 课程
- `people` → 学员
- `scheduling` → 班级、排课
- `lesson` → 课时
- `finance` → 订单
- `teaching` → 老师教室
- `marketing` → 渠道

## 3. 组件原语

当前已落地：

- `Shell`：后台壳层。
- `Sidebar`：分组导航。
- `Topbar`：当前机构和退出入口。
- `PageFrame`：页面标题、说明、动作区。
- `DataTable`：资源列表基础表格。
- `StatusPill`：统一状态徽章。
- `MetricCard`：看板指标卡。

后续新增页面必须优先复用这些原语。

## 4. 页面组合顺序

每个后台资源页按以下顺序组合：

1. `PageFrame`
2. 关键指标或过滤器
3. `DataTable`
4. 详情抽屉 / 独立详情页
5. 表单和危险操作

不要把表单放在页面主视觉之前，除非该页面本身就是创建向导。

## 5. 状态语义

状态颜色固定：

- `ok`：已完成、已缴费、已发布、进行中。
- `warn`：待处理、待跟进、已预约、排期中。
- `info`：已联系、已试听等中间状态。
- `danger`：无效、取消、退款、归档。
- `neutral`：默认或未知状态。

## 6. Public Web 标准

家长扫码端优先移动端：

- 页面要短，主按钮明确。
- 不要求家长登录。
- 表单字段只保留转化必要信息。
- 必须记录来源参数：`source`、`campaign`、`course`。
- 提交后只给明确成功反馈，不暴露后台术语。

## 7. 不允许的 UI 做法

- 不允许每个页面各自设计一套标题和表格。
- 不允许状态颜色在页面里临时写死。
- 不允许把业务资源散落在一个大页面里。
- 不允许等 MVP 做完后再重构 UI 壳层。
- 不允许让公开端复用后台组件。
